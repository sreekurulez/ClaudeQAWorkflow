# US-001 — Item inventory management with order safety

**Story ID:** US-001  
**Status:** Partially implemented (see AC-4)  
**Route scope:** `/items`, `/cart` (and `/profile` via shared `Header` dependency)

---

## User story

> As a store manager,  
> I want to manage items and their associated orders  
> so that I can keep inventory and order history in sync without accidentally breaking pending orders.

---

## Acceptance criteria

### AC-1 — View item list ✅ Implemented

**Given** I am logged in,  
**When** I navigate to `/items`,  
**Then** I see a list of all current items with their names.

- UI element: `data-testid="item-list"` (on `/items`)
- Implemented in: `src/pages/ItemsPage.tsx`, `src/components/ProductList.tsx`

---

### AC-2 — Add a new item ✅ Implemented

**Given** I am on the items page,  
**When** I fill in the "New item" field and click "Add item",  
**Then** the item appears in the list immediately.

- UI elements: `data-testid="item-name-input"`, `data-testid="add-item-submit"`
- Endpoint: `POST /api/items` → 201
- Implemented in: `src/pages/ItemsPage.tsx`

---

### AC-3 — Delete an item with confirmation ✅ Implemented

**Given** I am on the items page,  
**When** I click the "Delete" button for an item and confirm the dialog,  
**Then** the item is removed from the list.

- UI elements: Delete button (no `data-testid`, role-fallback), `data-testid="confirm-delete-button"`, `data-testid="cancel-delete-button"`
- Endpoint: `DELETE /api/items/:id` → 204
- Implemented in: `src/pages/ItemsPage.tsx`, `src/components/ConfirmDialog.tsx`

---

### AC-4 — Deleting an item with a pending order must be blocked ❌ NOT IMPLEMENTED

**Given** an item has at least one order with `status: "pending"`,  
**When** I attempt to delete that item,  
**Then** the delete is rejected with an error message such as  
_"Cannot delete: this item has pending orders. Cancel or fulfil them first."_

- This is a **missing feature**, not a bug or a selector issue.
- `DELETE /api/items/:id` currently deletes unconditionally — it does not check `ORDERS` for pending entries referencing the item.
- The confirmation dialog (`confirm-delete-button`) still appears; the block happens server-side and is surfaced to the user via a toast.
- **This AC is the fixture for Change 1 (user-story-driven planning):** a code-diff-driven test planner cannot plan a case for code that doesn't exist; a requirements-driven planner reading this document can.
- To implement: in `server.js`, before `ITEMS = ITEMS.filter(...)`, check `ORDERS.some(o => o.itemId === id && o.status === 'pending')` and return `403` with the error message. Then surface the 403 in `ItemsPage.tsx`.

---

### AC-5 — Cart shows current item prices ⚠️ gap: true (UI element missing)

**Given** I have items in my cart,  
**When** I view `/cart`,  
**Then** a summary line labelled "Price summary" shows the total cost of all cart items.

- Expected UI element: `data-testid="cart-price-summary"` — **does not exist yet**.
- `data-testid="cart-total"` exists and shows total via `<PriceDisplay>`, but it is not labelled "Price summary" and has no dedicated testid.
- **This AC sets `gap: true` at plan time** — the planner can flag the gap without waiting for a failing test.

---

## Deliberately unimplemented: AC-4

**Which AC is unimplemented:** AC-4 — delete blocked by pending order.  
**Why deliberately:** This is the "missing feature" category (distinct from a selector bug or a `SEED_BUG` product bug). It proves Change 1's thesis: requirements-driven planning finds this gap; code-diff-driven planning cannot, because there is no code to diff.  
**What would implement it:** A pending-order check in `DELETE /api/items/:id` (server.js) + a 403 handler in `ItemsPage.tsx`.  
**Do not implement it** until the user-story planning feature is validated against this gap.
